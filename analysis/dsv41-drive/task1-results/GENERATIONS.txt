GENERATION MANIFEST: how it is built, that it reproduces, and what it does and does not enforce.
Written 2026-09-21 by t1-armseries at team-lead's request. Manifest: clean-reference.json "generations" (tree id -> one-line label).

1. WHAT AN ID IS AND HOW IT WAS PRODUCED
There was no generating script. Each entry is `git rev-parse <commit>:python` (the git tree id of python/ at a commit) as its key, with a hand-written one-line label. task1_arm_verdict.py derives the SAME id at analysis time: generation() calls python_tree(root, head) = `git -C <root> rev-parse <head>:python`, where head is the commit the arm's own provenance says it imported, and looks it up in the manifest; a tree not in the manifest prints "GENERATION unknown: python tree <12 hex> is not in the manifest". The id names the code that ran: two commits with the same python/ tree ran the same sglang. It says nothing about scripts/dsv41 (the harness comes from the NEW worktree), the arm script or the verdict.
Reused unchanged for gen3: same key (full 40-hex tree id), same one-line label shape, same file, "generations" map only. The arm lists in the file (new:off, new:on, old:on) are untouched: no arm has been run at gen3.

3. GEN3 REGISTRATION
Key 8d3312fdf0a7ecc38dfe70e04d1badfd0ca91cf6 = `git rev-parse 8c78749b35:python`, also HEAD's python tree (HEAD a23480d2f2 when checked; it is the same at 5af2975164).
Commits separating gen3 from gen2 (87417376f5): 58 in total. Full list with classification: GENERATIONS-gen2-to-gen3.tsv. Only TWO touch python/ and both are BEHAVIOURAL:
  85cdbf9382 fix(exl3): skip sequence 0 when the service advances through the wrap, on both rings. File: python/sglang/kernels/jit/csrc/moe/exl3_ram_miss_host.cpp (a host C++ change: the JIT module is recompiled, so a gen3 boot compiles once). Effect: on each 0xFFFFFFFF wrap the service no longer spends an iteration on a record nobody posted (a spurious counter increment and stage record per ring per wrap). A wrap is one per 2^32 sequences, so a 4-session arm should never reach one; the change is expected to be invisible in decode tok/s. That is an expectation, not a measurement.
  8c78749b35 fix(exl3): refuse to attach an in-graph layer whose gather is wider than the service's lanes. File: python/sglang/srt/layers/moe/exl3_ram_miss.py. Effect: attach raises ValueError when graph_gather_rows > 8; startup only, nothing on the per-request path, and the commit says no working configuration is refused (DSV4.1 bs 1 is top-6).
Two more commits change a HARNESS, not python/, and so are NOT captured by the generation id: c87b8dc181 (scripts/dsv41/provenance.py resolves each drive's block device by st_dev instead of by name, and its idle check / read_sectors now raise on an unresolvable device; resolve_drive returns the filesystem's device, the PARTITION (nvme3n1p1), where the old name table read the whole disk (nvme3n1): per-session deltas agree, absolute cumulative sectors do not; measured on divix01 2026-09-21 the whole-disk minus partition difference was 2,608 sectors on nvme0, 42,400 on nvme2 and 4,296 on nvme4. An earlier line of this file said readings should be identical; that was wrong and is corrected here) and 6a2643c1b4 (the stage-trace overhead tool, not used by the arm script). d5e0c3423c added a comment to task1-baseline-arms.sh. The other 54 commits are documentation, tests, analysis or results only and have no effect on an arm.
BLIND SPOT OF THE SCHEME: an id names python/ only. Two arms can share a generation while the harness between them changed (c87b8dc181 is the live example), so a comparison across arms needs the harness commit compared as well as the generation. Not extended here; written next to the gen3 label in clean-reference.json too.
Consequences for anyone comparing a gen3 arm with a gen2 number: the comparison is NOT clean in principle (two behavioural commits, one of which recompiles the host module), even though both are expected to be inert on decode throughput. The pre-registered R1-style check (one arm, tracing off, at the new generation, judged against the previous generation's band) is the way to find out; it has not been run. The intermediate tree after only the wrap fix (bb14d742ade5728eae9c3016d72a549dd670b403, 85cdbf9382) is deliberately NOT registered: no arm ran there, and an arm run at that commit should print "GENERATION unknown".

Now: generation_gate() in task1-baseline-arms.sh runs once over the whole arm list before the first arm, also under DRY=1. It refuses (exit 5, sentinel ABORTED exit=5) when REFERENCE is unset or unreadable, when `git rev-parse <expected sha>:python` cannot be resolved, or when that tree is not a key of REFERENCE "generations"; there is no override. Limits of the gate: it checks the code generation (python/), not the harness (section 3 blind spot), and it does not check that the arm-list membership or the label text is right. It is not covered by a unit test (the script sources divix01-only paths); the observed outputs above are the evidence.
