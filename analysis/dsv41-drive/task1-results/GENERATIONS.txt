GENERATION MANIFEST: how it is built, that it reproduces, and what it does and does not enforce.
Written 2026-09-21 by t1-armseries at team-lead's request. Manifest: clean-reference.json "generations" (tree id -> one-line label).

1. WHAT AN ID IS AND HOW IT WAS PRODUCED
There was no generating script. Each entry is `git rev-parse <commit>:python` (the git tree id of python/ at a commit) as its key, with a hand-written one-line label. task1_arm_verdict.py derives the SAME id at analysis time: generation() calls python_tree(root, head) = `git -C <root> rev-parse <head>:python`, where head is the commit the arm's own provenance says it imported, and looks it up in the manifest; a tree not in the manifest prints "GENERATION unknown: python tree <12 hex> is not in the manifest". The id names the code that ran: two commits with the same python/ tree ran the same sglang. It says nothing about scripts/dsv41 (the harness comes from the NEW worktree), the arm script or the verdict.
Reused unchanged for gen3: same key (full 40-hex tree id), same one-line label shape, same file, "generations" map only. The arm lists in the file (new:off, new:on, old:on) are untouched: no arm has been run at gen3.

BLIND SPOT OF THE SCHEME: an id names python/ only. Two arms can share a generation while the harness between them changed (c87b8dc181 is the live example), so a comparison across arms needs the harness commit compared as well as the generation. Not extended here; written next to the gen3 label in clean-reference.json too.
Consequences for anyone comparing a gen3 arm with a gen2 number: the comparison is NOT clean in principle (two behavioural commits, one of which recompiles the host module), even though both are expected to be inert on decode throughput. The pre-registered R1-style check (one arm, tracing off, at the new generation, judged against the previous generation's band) is the way to find out; it has not been run. The intermediate tree after only the wrap fix (bb14d742ade5728eae9c3016d72a549dd670b403, 85cdbf9382) is deliberately NOT registered: no arm ran there, and an arm run at that commit should print "GENERATION unknown".

6. THE HARNESS IS NOT IN THE ID: WHAT WAS ASSESSED, AND WHAT WAS THEN BUILT (options C and A, 2026-09-21; B not built)
BUILT: (C) harness_gate() in task1-baseline-arms.sh, exit 6, also under DRY=1: wt-task1-new must be at EXPECT_NEW and clean whatever the arm's code (the harness runs from it for old arms too), and the runtime copies of the arm script and the verdict must equal their blobs at EXPECT_NEW; the $0 bug is fixed (SELF=readlink -f $0 before env-full.sh cd's) and the run.out header prints sha256 of the script, verdict, env-full.sh and gpu-run.sh, which are also stored in each arm's cache.json as runtime_sha256. (A) provenance.harness_loaded(): sha256 of every harness file the process actually loaded (from sys.modules and __main__ under scripts/ and analysis/, so a new import is recorded without editing anything; the by-path drive_conditions.py is registered in sys.modules for that), plus the harness worktree's head and dirtiness, stored as provenance.harness_loaded; the verdict prints a NOTE HARNESS line (or says the arm predates the record). Observed refusals and the sha chain are in section 4b below. The assessment that led here follows unchanged.

ASSESSMENT (before building):
What the harness actually is: three repo files (scripts/dsv41/trace_corpus.py; scripts/dsv41/provenance.py; analysis/dsv41-drive/drive_conditions.py, which provenance loads by path), two hand-copied runtime files outside any repo that also exist in the repo (analysis/task1-baseline-arms.sh and task1_arm_verdict.py under $CC/analysis/dsv41-drive), two divix01-only shell files that are in no repo (dsv41-phase3b/env-full.sh, gpu-run.sh), and the input sessions.jsonl.
What is recorded today: the arm json's provenance.harness_files is {trace_corpus: <path>} only, with no hash and no commit; provenance.git is the worktree the imported sglang sits in. For a NEW arm that worktree also supplies the harness, so git.head covers both. For an OLD arm the harness comes from wt-task1-new, whose HEAD and dirtiness are neither recorded nor checked (preflight checks only the worktree of the code under test). The arm script's own sha printed blank in task1e-run.out (`sha1sum "$0"` runs after env-full.sh has cd'd, so a relative $0 no longer resolves); the verdict's sha is printed (sha1-12).
Churn if the id were a directory tree: scripts/dsv41 touched by 33 of the last 333 commits, analysis/dsv41-drive by 75 (mostly documentation and unrelated tools): far too noisy. Over the three repo files: 13 of 333 (2 of the 70 since gen2, c87b8dc181 and 5203f9ffc7), about one registration event per 25 commits. The task1 arm script + verdict: 11 of 333.
Options, cheapest first:
 (C) two preflight checks, a few lines: for an old arm also require wt-task1-new clean and at EXPECT_NEW (the harness worktree is unchecked today), and require the runtime copies of the arm script and verdict to equal the repo blobs at EXPECT_NEW (stops hand-copy drift).
 (A) record, do not gate: provenance stores sha256 of the files it actually loaded (trace_corpus.py, provenance.py, drive_conditions.py from sys.modules / the loader, so a new import cannot escape a list), and the arm script records its own and env-full.sh / gpu-run.sh / verdict sha256 into the run.out header (fixing the blank $0 sha). About 30-40 lines and one test in test_provenance.py, an hour or two; no manifest. Makes "same harness?" a comparison of two arm jsons rather than a note.
 (B) register a harness id in the manifest and refuse unregistered harnesses at launch, same shape as generations: key = hash of the loaded-file hashes. About half a day with tests and one manual registration per harness change. Worth it only if a comparison starts to depend on it.
Recommendation: (C) and (A); keep the note "compare the harness commit as well" until (A) exists; do (B) on demand. Calibration: the harness changed after gen2 in ways that affect what is RECORDED and JUDGED (drive counters, the idle check), not the timed loop, so a harness change is more likely to move a gate than the decode rate; a change to trace_corpus.py's workload or timing would move the rate and is the case the id most needs to catch.
